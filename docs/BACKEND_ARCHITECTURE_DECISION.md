# 后端架构决策记录（ADR）

> 编写时间：2026-08-12
> 决策人：App 线
> 触发问题：为支撑移动 App 接入，后端是否需要从单体重构为微服务架构？
> 状态：**已决策**

---

## 决策

**不做微服务。** 后端继续保持 Java 17 + Spring Boot 单体，改造方向是**模块化单体（Modular Monolith）+ 面向 App 的版本化契约层**。

下面给出否决理由、替代方案的具体边界，以及不与在途重构冲突的推进顺序。

---

## 一、为什么否决微服务

不是"微服务不好"，是**这个系统当前的约束条件与微服务要解决的问题完全不匹配**。六条理由，每条都基于已核实的事实。

### 1.1 部署形态不支持，而且已经因此出过 P0 事故

生产是**单台服务器**，根分区 40 GB，当前可用约 8–11 GB。2026-04-27 曾发生 `POST /api/volunteer/generate` 全线 500，根因是根分区写满导致 MySQL 无法在 `/var/tmp` 写临时文件（见 `DEV_PROGRESS.md` v6.93）。

拆成 5 个服务意味着同一台机器上跑 5 个 JVM：每个 JVM 基础堆 + Metaspace 保守估计 300–500 MB，加上 5 份日志、5 份 JAR 备份、5 套发布产物。**这会把已经踩过的磁盘坑放大五倍**，换来的是零收益。

### 1.2 没有运维底座

当前发布方式是 `deploy_backend_safe.sh` + 单个 systemd unit `gzly`，健康检查是 curl 一个 `/metrics`。仓库 `git log` 只有 **5 个提交**，没有 CI。

微服务的前置成本是服务注册发现、配置中心、分布式链路追踪、服务间鉴权、熔断限流、灰度发布、N 条独立流水线。在连 CI 都还没有的情况下引入这一整套，团队的时间会全部消耗在基础设施上，业务停滞。

### 1.3 流量画像不匹配

这是**季节性**的公益工具，`/api/site-stats/online` 实测在线人数是个位数到两位数。微服务的核心价值是"不同模块能独立扩缩容、独立发布节奏、由不同团队独立所有"——**这三条在当前系统上一条都不成立**。

### 1.4 真正的痛点拆进程一个都不解决，反而会恶化

`docs/MULTI_PROVINCE_ALGORITHM_REFACTOR.md` 列出的核心问题是：

| 痛点 | 微服务能解决吗 |
|---|---|
| `VolunteerService` 4000 行 / 203 KB | 不能。这是类的内聚问题，拆进程只会变成"一个 4000 行的类被塞进一个独立服务" |
| 省份逻辑硬编码、配置散在三处 | 不能。这是配置事实源问题，靠数据库收敛，与进程边界无关 |
| `enrichWithAlgorithms` 96 条 N+1 查询 | **会恶化。** 内存方法调用变成网络调用后，N+1 查询变成 N+1 RPC |
| 缓存键含 `studentRank` 导致全 miss | 不能。这是缓存设计问题 |
| 非贵州省份数据缺口 | 不能。这是数据采集问题 |

**把内存调用换成网络调用，唯一确定得到的是延迟、故障率和调试难度的增加。**

### 1.5 系统已经有一个独立服务了，而且拆得正确

`ml-service` 是独立的 FastAPI + LightGBM 服务。这次拆分是对的，因为 **Python 运行时和 JVM 天然无法同进程**，是真实的技术边界。

也就是说当前形态已经是「单体 + 一个专用服务」——**这恰恰是这个规模该有的样子**。继续按业务域切 Java 侧，边界就不再是技术必然，而是人为制造的。

### 1.6 时机最差：在途重构尚未提交

当前工作区有 **15 个已修改的后端源文件 + 31 个新增未跟踪源文件**，全部未提交、未联调（`MULTI_PROVINCE_ALGORITHM_REFACTOR.md` 阶段 0–4）。

在一个还没入库、还没跑过集成验证的重构之上，再叠一层微服务迁移，是让项目永远发不出去的经典做法。

---

## 二、替代方案：模块化单体

微服务想要的**边界清晰、可独立演进、变更影响可控**，用包边界 + 编译期约束一样能拿到，且没有分布式代价。

### 2.1 目标模块边界

```
com.gzly
├── platform/          横切能力：Result、异常、鉴权、限流、缓存配置、合规词表
├── catalog/           院校库、官方链接、院校问答（读多写少）
├── scoreline/         分数线、一分一段、位次归一（RankNormalizationService）
├── policy/            省份档案、批次政策、就绪度门禁
├── recommend/         志愿推荐：编排 + 候选 Provider + 七层算法引擎
├── ai/                AI 解读、skills 对话、输出合规清洗
├── content/           公告、反馈、加油墙、特殊类型招生、站点统计
├── admin/             管理端（含数据导入）
└── api/
    ├── web/           现有 /api/** 控制器，服务 gzly-web
    └── app/           新增 /api/app/v1/** 契约层，服务移动端
```

### 2.2 依赖规则

1. `api/*` 只依赖各业务模块暴露的 **facade 接口**，不依赖其 `internal` 实现。
2. 业务模块之间**不允许直接互相调用 service 实现**，只能通过对方 facade。
3. 所有模块可依赖 `platform`；`platform` 不依赖任何业务模块。
4. `recommend` 依赖 `policy` / `scoreline` / `catalog` 的 facade，反向依赖禁止。

### 2.3 约束靠测试强制，不靠自觉

引入 **ArchUnit**，把上述规则写成单测。这是模块化单体与"包名看起来分了层但实际互相乱引"的唯一区别——**没有编译期或测试期强制，包结构在三个月内必然退化**。

```java
// 示意：禁止跨模块访问 internal
noClasses().that().resideInAPackage("..api..")
    .should().dependOnClassesThat().resideInAPackage("..internal..");
```

### 2.4 什么时候才该考虑微服务

给一个明确的触发条件，避免这个决策被反复拿出来讨论：

- 单机资源确实撑不住，且垂直扩容已到顶；**或**
- 出现了真实的独立扩缩容需求（例如 AI 解读峰值把生成链路拖垮，且限流无法解决）；**或**
- 团队规模到了多个小组各自拥有独立发布节奏。

**在这三条中任何一条成立之前，拆分都是净负债。** 届时模块化单体也已经把边界切好了，拆分成本远低于现在从泥球里硬拆。

## 三、面向 App 的契约层（本次真正需要新增的后端能力）

App 接入带来的**唯一真实架构需求**不是微服务，是**稳定、精简、版本化的契约**。

### 3.1 问题

| 现状 | 对 App 的影响 |
|---|---|
| `VolunteerItem` 75 个字段，其中 64 个可选（85%） | 客户端 DTO 全是嵌套 optional，UI 到处要写兜底 |
| 生成一次返回 96 条完整 item | 弱网下单个响应体巨大，解析与渲染都慢 |
| `default-property-inclusion: non_null`，null 字段直接消失 | 字段存在性不可预测 |
| 六套语义重叠的评分字段并存 | 客户端无法判断该展示哪个 |
| 无版本化，Web 改字段 App 直接崩 | 两端发版节奏不同，Web 可随时刷新，App 有存量版本 |

### 3.2 设计

新增 `api/app` 模块，提供 `/api/app/v1/**`，与现有 `/api/**` **并存互不绑架**。

**列表与详情分离**：

- `VolunteerItemBrief`：列表用，约 20 个字段，**全部必填**（服务端负责给默认值，不下发 null）。包含序号、院校名、专业/专业组名、城市、梯度、机会指数、数据可信度、风险标签、是否需人工复核。
- `VolunteerItemDetail`：点开单条时按需拉取，承载证据链、历史记录、算法解释、扩招/供给指数等重字段。

96 条 brief 的响应体相比现状可压到约四分之一，而且客户端 DTO 不再有 85% 的可选字段。

**实现方式：纯投影，零回归风险。** `api/app` 只做 `VolunteerItem → Brief/Detail` 的字段映射，不改 `recommend` 模块内部模型，不改任何现有文件。**全部为新增文件**，因此与在途重构的合并冲突面接近于零。

**版本策略**：路径版本（`/v1/`）。字段只增不删；确需破坏性变更时开 `/v2/` 并保留 `/v1/` 至少一个招生季。

## 四、算法架构的四项决策

算法的核心设计（等效位次换算、对数位次 CDF 概率模型、退档折减、等渗校准、梯度归属）已在 `MULTI_PROVINCE_ALGORITHM_REFACTOR.md` 第九至十一部分完成，且阶段 0–4 已编码。本节只补该文档未覆盖、且直接影响 App 的四项。

### A1 · 删除六个空壳引擎类

`com.gzly.algorithm` 下 `MlPredictionEngine`、`PolicyRuleEngine`、`ComplianceGuardEngine`、`SkillsRagEngine`、`ExportEngine`、`AiDeepAnalysisEngine` 六个类各约 500 字节，**全项目零引用**。

留着空壳是负债：新人（和 AI）读代码时会以为这些能力存在，从而做出错误的架构判断。需要时再建，成本是分钟级。

### A2 · 对外只暴露两个数字

当前一条志愿上并存六套评分：`recommendationScore`、`precisionScore`、`chanceScore`、`matchScore`、`dataConfidence`、`dataConfidenceScore`，另有新增的 `calibratedProbability`。**用户无法理解，客户端也无法判断该展示哪个。**

决策：`api/app` 的 Brief 对外**只暴露两个数字**——

1. **机会指数**：取 `calibratedProbability`（等渗校准后的值），不再暴露未校准的 `chanceScore`。理由是校准后的数值才具备"62 分大致对应 62% 历史达线频率"的可解释性，而这正是用户会追问的。
2. **数据可信度**：合并 `dataConfidence` / `dataConfidenceScore` / `precisionScore` 为单一维度。

其余评分降级为 Detail 中的解释性字段，不进列表。合规上机会指数**必须称"机会指数"，禁止称"录取概率"**。

### A3 · 排序必须回到后端

当前「冲刺型 / 保守型」视图的重排逻辑在前端 `gzly-web/src/utils/volunteer-plan.ts`（`ambitionScore` / `safeScore` 加权后重新编号）。

这是错的，两个理由：

- 这是**业务逻辑不是展示逻辑**。同一份方案在 Web 和 App 上顺序不同，是用户会直接察觉并投诉的缺陷。
- 两端各维护一份权重公式，必然漂移。

决策：`POST /volunteer/recommend` 接收 `strategyMode` 后**直接返回已排好序的列表**，客户端不再重排。过渡期 App 先原样移植该文件并加单测锁定逐值一致，后端接管后删除客户端副本。

### A4 · 就绪度必须能升到 FULL

`ProvinceReadinessService` 当前注释写明「阶段 0 尚无判定来源，`FULL` 恒不返回」，最好状态是 `ESTIMATE`。

后果是**每一份方案都必须打「历史估算」角标**，包括数据最完整的贵州。这会持续削弱产品可信度。需要定义 `FULL` 的判定来源（建议：当年官方计划与投档线已导入 + 回测指标达标）。在此之前，App 侧照实标注，不美化。

## 五、推进顺序（避免与在途重构冲突）

后端工作区当前有 46 个未提交文件。顺序按"冲突面从小到大"排：

| 阶段 | 内容 | 冲突风险 | 前置条件 |
|---|---|---|---|
| **P0** | 在途重构（阶段 0–4）**先提交并联调通过** | — | 由后端线完成 |
| **P1** | 新增 `api/app` 契约层（纯新增文件） | 极低 | P0 完成 |
| **P2** | 删除六个空壳引擎类（A1） | 极低（零引用） | 任意时点 |
| **P3** | 排序回后端（A3） | 中（动 `recommend` 与 Web） | P0 完成，且与 Web 线协调 |
| **P4** | 包结构按第二节切分 + ArchUnit | 高（大范围移动文件） | P0 提交后单独一轮，期间冻结其他后端改动 |
| **P5** | `FULL` 就绪度判定（A4） | 中 | 依赖数据采集进度 |

**App 侧不阻塞在任何一项上**：M0 直接对接现有 `/api/**`，客户端内部先做一层 DTO 收敛，等 `api/app` 上线后切换。这样 App 的排期与后端改造解耦。

## 六、这份决策没有覆盖的

- 数据库拆分：不涉及，继续单库。
- 消息队列：当前无异步场景需要，不引入。
- 网关：单体 + Nginx 已足够，不引入独立网关。
- 容器化：可选优化，但在单机部署下收益有限，不列为必需。
